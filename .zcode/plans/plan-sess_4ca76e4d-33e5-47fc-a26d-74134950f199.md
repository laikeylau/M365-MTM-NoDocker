# M365-MTM 平台优化改造计划

## 诊断结论（简述）

项目是 CIPP 的 Linux 移植版（PowerShell 后端 534 端点 + Next.js 前端 304 页面），"重"的根源有四个：① Azurite 只是 Azure 存储模拟器（Docker + 3 端口），而后台任务在 Linux 上本来就被禁用，模拟器价值很低；② 服务器上要装 Node.js 现场构建前端（~98 个 npm 依赖）；③ 部署链断裂——`cipp-server.ps1` 被文档引用但仓库不存在，`deploy.sh` 期望的目录结构（CIPP-API/）与实际（backend/）不符；④ 大量死代码（93 个演示模板文件、重复仪表盘、未用依赖）。关键可行性验证：全库仅 9 个存储命令、301 处调用、OData 过滤只有 `PartitionKey/RowKey/属性 eq` 简单子集，队列仅 4 处引用——**SQLite 兼容层替代 Azurite 完全可行**。AdminDroid 的核心是"以报告为中心"（服务→分类→报告树，行内执行操作），而项目已有 72 类缓存数据集 + CippTablePage 行级动作基础设施，具备对齐条件。

## 轨道 A：部署减重（彻底去 Docker 化）

**目标：必备组件从 6 项（Linux + Docker + PS7 + Node + SSL 证书流程 + Windows 机器）降到 2 项（Linux + PowerShell 7）。**

### A1. SQLite 存储层替代 Azurite
- 新建 `backend/Modules/AzTablesShim/` 模块，以**同名命令**实现 AzBobbyTables 的 9 个接口：`New-AzDataTableContext`、`Get-AzDataTableEntity`（57 处）、`Add/Update/Remove-AzDataTableEntity`（228 处）、`New/Get/Remove-AzDataTable`、`Clear-AzDataTable`、`Remove-AzDataTable`，底层用 `Microsoft.Data.Sqlite`（DLL 放入 `backend/Shared/`，与现有 AppInsights/CIPPSharp 同模式加载）
- 表结构：`(PartitionKey, RowKey)` 复合主键 + 时间戳 + 属性 JSON 列；实现 OData 过滤子集翻译器（`eq/ge/lt/and` → SQL WHERE，覆盖抽样确认的全部用法）；实现批量事务（`Invoke-AzDataTableTransaction` 如有使用）
- 队列（`Add-CippQueueMessage` 等 4 处）映射到 SQLite 的 `cippqueue` 表；Blob 用途检查后用文件系统目录或 BLOB 列承接
- 在 `backend/profile.ps1` 中让 Shim 模块优先于 AzBobbyTables 加载（保留原模块目录作为回退，后续删除 4.9M 的 AzBobbyTables）
- Linux 模式下密钥固定存 SQLite（复用 `CippLocalAuth`/DevSecrets 模式），移除 Key Vault 代码路径（TROUBLESHOOTING 已知问题 4）
- 提供可选迁移脚本 `scripts/Migrate-AzuriteToSqlite.ps1`（读旧表写 SQLite）

### A2. 直跑组件：API 守护 + Web 服务
- **补写 `cipp-server.ps1`**（仓库根目录）：环境变量装配（含 `DisableCIPPRestMethod=true`）、启动 CIPPHttpTrigger 监听 :7071、日志重定向、优雅退出
- **systemd 单元** `deploy/systemd/cipp-api.service`：`Restart=always`，替代手工 `pkill/重跑` 流程
- **Caddy 替代 nginx**（单二进制、自动 HTTPS 免 certbot）：静态托管 `frontend-dist/` + 反代 `/api/*` → :7071 + 保留 `/.auth/*` mock 端点 + 迁移 nginx.conf 的登录/注册限流规则；提供 `Caddyfile` 模板

### A3. 前端预构建 + 死代码清理
- 服务器零 Node：`frontend-dist/` 作为发布产物（提供本地构建脚本 + 可选 GitHub Actions workflow），Caddy 只吃静态文件
- 删除：`frontend/src/sections/dashboard/`（93 个未引用的 Devias 演示文件）、11 个占位页、`theme-backup-202605141658/`、重复版本（dashboardv1、onboarding.js 旧版、重复的 tenantlookup/bpa-report-builder 占位）、死代码（`ReportDashboard.jsx`）
- 移除未用依赖：`react-grid-layout`、`@nivo/*`、Formik、`react-quill`、`react-beautiful-dnd`、双虚拟滚动择一保留（保留 react-window）、图表库归一（保留 ApexCharts，去掉 Recharts/Nivo 的单一引用点）、Redux（仅剩 toast 一个 slice，迁移到 context 后移除）

### A4. 安装与残留清理
- 新写 `install.sh`：检查 pwsh → 初始化 SQLite → 生成 systemd unit + Caddyfile → 启动自检，一键完成
- 废弃 `deploy/docker-compose.yml` 与旧 `deploy.sh`（目录结构断裂）；`scripts/` 中硬编码的 `/root/cipp-deploy/...` 路径改为脚本自身定位或环境变量
- Windows 残留：EXO RBAC 设置脚本改用 Graph REST 调用（或验证 ExchangeOnlineManagement v3 在 PS7 Linux 的可用性后改写）；`IntuneWin*.exe` 移入可选工具目录
- README 重写为"两组件部署"版本

### A5. 后台任务自持（去 Azurite 后必须）
- `cipp-server.ps1` 内置后台调度 runspace：驱动 `backend/Config/CIPPTimers.json` 的 28 个 cron 任务（复用现有 `Receive-CIPPTimerTrigger` 的调度评估逻辑）+ 轮询 SQLite 队列表，替代 Azurite Queue + 已禁用的 Durable Functions
- 提供 systemd timer 备选方案文档

## 轨道 B：AdminDroid 式统一报告中心 + 行内操作

### B1. 报告注册表（单一事实来源）
- 新建 `frontend/src/data/report-registry.js`（配合后端无改动优先）：每份报告定义 `{ id, service, category, nameEn, nameZh, source: ListX 端点 | DBCache 类型, columns, filters, defaultSort, rowActions[], exportable, chartType }`
- 首批注册 30~40 份报告：现有各节分散报告页（Email 12 份、Identity 5 份、Tenant 4 份、Security/Intune 报告）+ 72 类 DB 缓存（`backend/Config/CIPPDBCacheTypes.json`）中适合报表化的数据集（用户/组/许可/MFA/风险登录/设备/CA 策略/邮箱统计…）——这部分是 AdminDroid 式增值：**不写新后端代码就能多出几十份报告**

### B2. 统一报告中心 UI
- 新路由 `/reports/:service/:reportId`，左侧树导航：**身份与访问 / 许可与订阅 / 邮件与 Exchange / 协作（Teams·SP·OneDrive）/ 端点与 Intune / 安全与合规** → 分类 → 报告（AdminDroid 式）
- 复用 `CippDataTable` 渲染：列筛选、全局搜索、CSV/PDF 导出、图表视图、保存视图（localStorage）、现有租户选择器 + "全部租户"跨租户聚合模式（DB 缓存数据自带租户维度，天然支持 AdminDroid 式跨租户报告）
- `src/layouts/config.js` 中各节的 Reports 子菜单折叠进报告中心入口，旧报告页路由重定向到报告中心对应报告

### B3. 行内操作（可操作报告）
- 利用 `CippTablePage`/`CippDataTable` 已有 `actions` 基础设施 + `CippApiDialog`/Drawer：注册表中每报告声明 `rowActions` → 行内菜单直接调用现有 534 端点中的 Exec 类端点
- 首批示例：用户报告行内（改许可/重置 MFA/禁用/临时密码）、邮箱报告行内（改转发/权限）、设备报告行内（同步/擦除）——零新后端代码

## 实施顺序与验收

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| Phase 1 减重 | A1–A5 | 干净 Ubuntu 上仅装 PowerShell 7 即可 `install.sh` 一键部署跑通登录+租户列表；`docker`、`node`、`npm` 全程未出现 |
| Phase 2 报告中心 | B1–B3 | 报告中心 30+ 份报告可筛/可导出/可跨租户；行内操作执行成功；旧报告页重定向无死链 |
| Phase 3 双语 | C | 中英切换即时生效；导航+报告中心 100% 双语 |
| Phase 4 收尾 | 文档+验证 | README/迁移指南/RUNBOOK 更新；全流程部署演练通过 |

## 主要风险与对策
- **AzBobbyTables 兼容性**：OData 翻译只做已用子集；用 `CIPPTests` 模块思路写接口回归清单（301 处调用按命令×过滤器形态抽样验证）
- **队列语义差异**：CIPP 队列仅 4 处、低频，SQLite 轮询足够；不做分布式语义
- **i18n 工程量**：按批次交付，第 1 批即可覆盖 90% 日常界面
- **功能域裁剪**：你未选择使用场景，故不删任何功能模块，仅清死代码与整理导航；后续如需裁剪（GDAP/Hudu/Sherweb 等）可在此基础上单独进行
